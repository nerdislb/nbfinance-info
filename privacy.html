Privacy/security contact: security@nbsystems.dev. This contact is not a claim that a statutory data protection officer has been appointed. nbfinance is not offered as a public banking service.

The information website

This website consists of static HTML and CSS. It has no account system, contact form, banking intake, payment flow, application analytics script, advertising or third-party asset embeds. Its own code does not set cookies or browser storage. This does not describe or limit the hosting provider's infrastructure or external sites.

GitHub Pages serves the site. GitHub documents that visitors' IP addresses are logged and stored for security purposes, even without GitHub sign-in. Its privacy statement describes processing in the United States and other countries. nbfinance does not set GitHub's log retention or promise EEA-only hosting.

Read the GitHub Pages documentation and GitHub Privacy Statement. This IP logging is performed by GitHub's hosting infrastructure, not by this website's own code.

No authorisation callback is hosted here. Opening these pages does not retrieve bank data. Never place financial information, tokens or codes in these URLs, the public repository or public comments.

The intended private pilot

The purpose is a manually initiated local inspection of booked balances for exactly two own/co-held EUR current accounts. There is no public user registration or service for other people. No transaction history, card feed, payment initiation, combined balance, spending allowance, background polling, phone transfer or financial-result archive is included.

The operator first approves provider configuration and, separately, account linking in the official provider/bank interface. Linking whitelists accounts; it is not the application's later API authorisation. A separately approved application run then uses the official provider/bank flow for authentication and account selection. The application does not collect bank-login PINs or TANs.

Session/account metadata is received before local confirmation. Full IBANs are shown privately before either balance is read. An unacceptable account response is rejected as a whole, with no balance read; extra metadata may already have reached process memory.

The two IBANs have a 30-second input window. After acceptance, the screen can remain visible during balance reads and session cleanup until a result replaces it or the application exits. Refusal or timeout prevents any balance read, but the screen can remain visible during session cleanup until exit. Only the later complete IBAN/balance result is released after verified API-session cleanup, then displayed for 20 seconds or a key. No partial result is treated as zero.

Data and recipients

The private application handles its configuration, bank identity, signed request tokens, random state, callback codes, session/account identifiers and identification hashes, account metadata, balances, currencies and dates. Bank responses can contain IBANs, holder/co-holder names, account products and extra balance types or references. Only the intended accounts and validated booked balances are used in the result.

The source is the bank through Enable Banking Oy, Finland, plus the operator's confirmations. Affected people can include co-holders. Their information must remain private; they should be informed about the intended use as appropriate. Local account confirmation does not itself prove legal ownership or provider eligibility.

The bank and Enable Banking necessarily process requests and connection metadata. Their own services and obligations are governed by their notices; they are not all asserted to be merely nbfinance processors. The provider's API notice also describes compliance/financial-monitoring and service-statistics purposes. No real financial payload is intended for GitHub, email, AI tools or public issue trackers.

Read the Enable Banking API Privacy Notice and API End-User terms. The separate website/Control Panel notice applies to that different scope. Read the current notices actually presented in any later approved official flow.

Storage and retention limits

The pilot handles financial payloads and flow secrets in its finite process and writes no financial-result files, database, snapshot or export. Signing-key files and separately retained configuration have their own persistent lifecycle. Normal output contains technical status or public bank catalog metadata, not account identities or financial values.

This is not guaranteed erasure, encrypted-memory protection or a secure-display promise. Process-reference disposal does not certify zeroisation. Terminal recording, screenshots, clipboard/browser history, OS swap/crash dumps, same-user/root access or abrupt host failure can preserve or reveal data. The foreground clipboard helper offers the authorisation URL for at most 30 seconds; another clipboard manager may keep it longer. Real access must not run inside AI terminal tools or screen capture.

The application requests an API session of at most 600 seconds, capped by the bank catalog, and a separate 300-second callback window. The bank consent can last longer. A known session receives a deletion attempt and readback after acknowledgement. Closure must not be assumed after an error, unknown session ID or abrupt interruption.

The API Privacy Notice dated 7 March 2025, checked on 3 November 2026, states: payment-account information is retained for format conversion for at most 60 seconds; authorisation credentials for up to 15 minutes; session-persistence data for the requested period up to 180 days; and IP/user-agent information for 30 days. These are attributed provider statements, not independently audited deletion guarantees for every possible record. The notice describes EEA processing by its listed API cloud providers, not an EEA-only guarantee for all involved services.

The website/Control Panel notice dated 17 March 2025 states indefinite retention of personal data and describes some US processing for website/administrative services. This is not a statement that API balance payloads are retained indefinitely. Consult the current notices before any real use.

Email correspondence

Email is separate from the application's ephemeral bank results. The operator and existing mail service can process a sender address/name, message content, attachments and technical headers to answer a request or handle an incident. Unsolicited sensitive information can still arrive despite the warning not to send it.

The existing contact service is Purelymail, operated by Add Rabbit LLC. Its FAQ states that it is based in the United States and uses AWS US-East-1 in northern Virginia. Its security page says backups of deleted email messages remain for one month. Deleting a message does not immediately delete every client/server/backup copy. Ordinary email is not promised to be end-to-end encrypted.

Read Purelymail's privacy policy, security documentation and location FAQ.

Proposed correspondence procedure: manually review messages when a matter is resolved and delete them when no longer needed to respond, handle an incident, meet a specific obligation or address a claim. Continued retention needs a reason and next review date. There is no deployed automatic mailbox-deletion process in this pilot.

Purpose-specific legal applicability and roles for public contact/hosting, contact monitoring, and any required processing terms and transfer safeguards remain adoption checks. No account-specific agreement or EU-US transfer mechanism has been verified for this notice. This is not a finding that the existing services are unlawful or that every private email requires such an agreement.

Legal scope and rights

The intended account use is a natural person's purely private household activity, but the household exemption is not a blanket exemption for public website/contact processing or the bank/provider's own services. Any professional, commercial or unrelated third-party use is outside this pilot and needs a fresh assessment.

Where GDPR applies, the proposed basis for voluntary correspondence and necessary operator-side incident handling is Article 6(1)(f): responding to the request and managing incidents, subject to necessity and overriding interests/rights. Article 6(1)(c) is relevant only to processing required by a specific applicable legal obligation. These are proposals for operator adoption, not legal bases assigned to GitHub, the bank or another provider. Visiting a page, local confirmation and bank PSD2 consent are not blanket GDPR consent.

Where applicable, you may request access, correction, erasure or restriction, object to legitimate-interest processing, and seek portability where its conditions are met. GDPR consent can be withdrawn for future processing where that is the actual basis. Statutory exceptions and other people's rights can limit a request.

The proposed response procedure follows applicable deadlines, generally one month under GDPR with only permitted extensions and notice. Statutory duties apply regardless of policy adoption. Requests cover existing data within the operator's responsibility, including applicable provider copies; they do not authorise a new bank retrieval to reconstruct data no longer held. Independently controlled bank/provider records must be addressed with the relevant entity.

Use the contact above for the operator's processing. You may complain to the Austrian Data Protection Authority or another competent authority. Its rights guidance explains the conditions.

Stopping access and changes

Refusing the local account check means no balance is read or displayed. Not running the application stops new requests, but does not necessarily end existing provider/bank sharing. API-session closure, Linked Account removal, termination of provider sharing, bank-consent revocation and legal erasure are different actions. Use the official provider data-sharing controls and bank channels as appropriate.

This draft is information about a narrow configuration, not a legal-compliance certificate or permission for bank access. Additional identity/site disclosures and applicable hosting/contact arrangements still need assessment before adoption; no unapproved address or phone number is invented. Material scope, storage or recipient changes need review before use. See the usage draft.
